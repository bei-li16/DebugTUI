U10 近期界面与项目切换：检查 App::new 项目重建是否正确清理旧 worker/通道/请求/缓存并保留应保留的用户设置；Watch/Locals 一变量一行是否保留嵌套展开、作用域、值更新、选择/滚动/鼠标命中和写入对象定位。核查宽矮/窄高/小窗口、zoom、快捷键、命令面板过滤、Setup 滚动提示及状态/请求常量替换的一致性。结构重构与“只是改常量”的提交也按实际 diff 检查行为，不能只读提交标题。

U11 测试与交付真实性：检查单元/真实 worker/MI/Tcl/实际 EXE 测试是否经过生产入口，预期是否独立，失败是否被跳过或靠放宽断言掩盖。区分 mock、真实本机工具、后端生产 C 模型、硬件 case 准备与实板执行。核对旧证据的源码 SHA、命令、工具版本、退出码、用例实际结果和保留日志；已清理日志记为当前不可核验，不能因此断言历史测试从未执行。只读核对源码/tag/Release/附件摘要及发布状态；不把正式 latest 与 prerelease 混为一谈，不把相同版本字符串当作二进制相同，不把发布版测试覆盖自动转移给后续 HEAD。

U12 汇总复核与交付：交叉检查所有高优先级问题及所有“通过”的边界，完成矩阵、证据、修复优先级和剩余限制，核对冻结输入是否变化，交付报告后结束本 Goal。

五、验证方法、空间控制与迭代方式

先静态审阅和复用可验证证据，再运行具体风险相关的最小测试。遵循现有 TESTING.md 和 runner 的真实参数；适用时运行 cargo fmt --all --check、cargo test --locked、cargo clippy --locked --all-targets -- -D warnings 及目录生成一致性检查。不要为了检查手册加载重新编译全套后端。

对同一冻结源码最多进行一次最终完整软件回归；新增复现或发现失败只补跑受影响范围，无源码/工具变化或新疑点不重复全量测试。每个新增测试必须能证明用户可见的行为或具体风险，不能镜像实现、只匹配日志文本、用生成器自己的输出作唯一期望。记录 PASS/FAIL/SKIPPED/NOT_RUN，不把未选套件计为通过。

本机此前 C/F/G 盘曾被构建与证据占满：
- 开始及大测试前检查可用空间、现有构建目录和活动进程；不打断其他测试或删除其输出。
- 只使用一个固定、可复用的 CARGO_TARGET_DIR，串行安排大构建，不在 C/F/G 各复制一套 target、OpenOCD、源码包或工具链。
- 需要新审计构建时优先关闭增量并降低非必要调试信息；这些设置与生产构建的差异必须记录，性能对比双方使用一致设置。
- 每个涉及卷预留至少 10 GiB；按现有构建规模保守估算峰值。预计触及保留空间就不启动该大构建，改做可完成的静态/小型验证，记录不能执行的证据缺口，不能改到另一盘继续灌满。
- 证据保留最小复现、必要原始日志、命令/版本/摘要及结果；不反复保存整套 JSON 快照、PDF 渲染页、安装包和 build 副本。PDF 按需提取与渲染特定页，复用已有索引。
- 保留会话记录、用户代码、工具链和输入文档。只清理本次创建且确认不再使用的临时产物；执行前核验绝对路径且不穿越 reparse link，不按 target/build/artifacts 名称全盘批量删除。

固定工作包 U01～U12，不临时增加宏大功能目标。每轮选择可完成的工作包或其明确子项，持续保存可恢复状态。每轮更新：
1. 完成了什么、核对了哪些具体行为、得到什么证据；
2. 还有什么未审、当前阻碍及下一步；
3. [审计工作包已完成数]/[未完成数]，分母固定 12；另列 36 项 feature 的审计状态分布，不能把两种计数混为开发完成数；
4. 新增或变更的问题 ID、测试结果、适用源码 SHA、证据位置及构建空间变化。
一次等待超时不代表进程失败，先查原进程和日志，禁止重复启动相同测试。不要反复生成 Goal、改计划或重复扫描充当进展。对于同一外部证据缺口，已完成适用本地来源及必要官方来源核查后仍无结论的，记录查证过程和不确定范围；继续独立项，不因等待硬件或已删除历史日志无限延长审计。未进行的工作不能简单改名为“证据不足”以假装完成。

六、交付文件与结论要求

在 G:\Data\GitFiles\DebugTUI\artifacts\development-audit\<冻结SHA前12位>-<时间戳> 创建本次独立输出目录（不得覆盖已有目录），至少交付：
1. report.md：中文审计报告，先给重要问题和影响，再给架构差异、M/R/多核支持、近期优化回归、证据质量及发布可信度，附明确支持边界和最小修复顺序。
2. requirements-matrix.json：36 项逐项结论、关联规格/TODO ID、代码位置、证据、适用 SHA 和验证缺口；另列长期需求与批准延期，不篡改原账本。
3. findings.json：稳定问题 ID、优先级 P0/P1/P2/P3、状态、影响对象、具体触发条件、预期/实际、代码绝对路径和行号、手册依据、最小复现/测试、建议修复范围、受影响 feature。区分实现缺陷、目录资料问题、文档漂移和证据不足；同一根因不要按寄存器数重复累计。
4. evidence/ 与 manifest.json：实际命令、cwd、工具/环境版本、开始结束时间、退出码、原始必要日志、文件摘要，以及输入/可执行文件/发布附件与源码的对应关系。大文件保留一份并引用。
5. audit-state.json：本次唯一实时审计状态；记录冻结基线、U01～U12、完成计数、已核对证据与缺口。历史开发账本保持原样，断点续跑先读取这里，不重做已完成工作。

每个结论使用明确状态：已核实通过、已确认缺陷、部分支持、证据不足、批准延期或不适用。已确认问题必须有实际代码因果链或可复现证据，不把猜测写成缺陷；无法复现但存在具体疑点时说明还缺哪项验证。通过结论也要说明证明范围，不能只列测试总数。

本 Goal 的完成条件：U01～U12 均有实际审阅与交付；36 项都有适用证据与明确结论；冻结范围内近期提交均被审查；reference 已完成约定的全量结构/继承、已有问题和风险语义复核并如实披露覆盖边界；可执行验证已完成或给出具体不可执行依据；所有重要问题可定位、可复现或有充分静态证明；最终报告、矩阵和 manifest 一致且输入漂移已说明。

审计完成允许仍有未修复缺陷、资料冲突及明确的硬件证据不足，不要求软件零缺陷才结束。资料的全量逐域语义认证、生产修复、扩展功能、上板、安装和新 Release 均不是本次结束条件。交付时给出明确建议：当前源码/参考目录/已发布版本各能信任到什么范围、是否存在阻断使用或后续发布的问题、推荐先修哪些项。不得因为有后续修复事项就继续无限开发。
