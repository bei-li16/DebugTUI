## 三、架构与实现要求

### A. 公共模型与配置

- 每核可独立选择 CPU、寄存器目录和访问参数，支持同型多核、非连续核编号及 M7＋M4 异构多核，保持旧项目与模板兼容。
- 区分芯片拓扑/连接参数、核型号寄存器定义和后端访问能力。落实规格的分层、解析优先级和来源可见性，映射到现有 `debug.toml`、`debug-env.toml`、芯片 profile 和核目录体系，保持兼容，不为复制草案目录结构而推倒重写。新的配置或参数模板必须写清声明位置、默认值、覆盖方式和实际读取路径。
- 寄存器编码、字段和复位值属于核描述；芯片配置可提供特性、路由和覆盖参数，不得悄悄改写核描述。配置声明与实际 ID/能力观测分别保留，冲突时展示双方来源和原因。
- 公共定义采用 `extends`，核型号只写增量；重名必须显式 `override=true`，拒绝循环、过深继承、歧义和不完整覆盖。保留每项定义的声明文件与继承链。
- 补齐可选 reset、结构化 source、confidence、present_if、访问条件和读副作用。条件使用有限的结构化比较，不引入表达式语言或脚本引擎。存在性、权限、后端能力和副作用分别判定。
- 保留 GDB、MMIO、CP15/MRRC、Banked、VFP、Backend 和 Alias 等现有必要访问路径。显示、字段和格式复用统一模型；显示分组不授予访问能力，RO/RW 标签不授予 writer。
- 明确 core、cluster、chip、unknown 归属。样本、缓存和 Watch key 包含实际 owner、访问核心及上下文；未知 owner 不猜测、不发数据读取。Alias 继承父项的归属、实现条件、访问条件和副作用限制。
- 复用已完成的 3～5 项代表定义验证。仅按本版需要迁移正式目录，避免继续扩大 R52 大目录。新增定义有来源；旧定义缺失来源时保留 Unknown，不编造批量元数据。

### B. Cortex-M3/M4/M7

- 内置 `armv7m-common`，提供 M3/M4/M7 增量目录。包含常用 SCB、NVIC、SysTick、MPU、Debug 状态，以及 DWT/FPB 的身份和容量。
- 使用官方 CMSIS 核头文件及 Arm 架构/TRM，提供可重复生成与检查的离线转换流程，复用现有工具。固定来源版本/提交、记录摘要和来源行，保留 Apache-2.0 声明；组合状态寄存器按正确位域拆分。CMSIS 未提供的复位值或副作用规则另找手册依据。
- SCB 覆盖常用控制/状态及 CFSR、HFSR、MMFAR、BFAR 等故障字段。本版不要求完整异常压栈帧恢复与 HardFault 函数定位。
- CPUID 驱动核型号核对；ICTR 只用于中断线数上限和寄存器 bank 数，不将上限等同全部实际中断。真实中断列表使用 SVD；MPU_TYPE 等驱动实际实例容量。
- NVIC 优先级位数从 SVD 或显式配置取得；缺少依据为 Unknown。本版禁止向 IPR 写入来探测实现位数。
- M MPU 支持 TYPE/CTRL/RNR/RBAR/RASR 及有效 region 的只读展示。间接 region 读取复用受保护的 selector 事务，保存、选择、读取、恢复并验证，不改变 MPU 配置。
- 对 DWT/FPB/FPU 等可选模块核对实现和使能条件。需要 DEMCR.TRCENA 或其他使能位时展示 NeedEnable；不得为完成探测自动使能。未启用时缺失的数据不能被当作“不存在”的证据。
- M4 增量覆盖 FPU 配置和身份，如 CPACR、FPCCR、FPCAR、FPDSCR、MVFR。通用寄存器堆和已有浮点视图优先复用 GDB/MI；不另造 DCRSR/DCRDR 调试器。
- M7 增量覆盖常用 cache/TCM 配置，如 CLIDR、CTR、CCSIDR、CSSELR、CACR、ITCMCR、DTCMCR、AHBPCR。需要 selector 的读取按事务处理；维护命令、写专用寄存器可以展示定义，不能作为普通读取执行。
- CorePrivate 使用各核自己的 AP/target。同一 PPB 地址在 M7 与 M4 上必须经独立的正确路由访问，验证值、目录、错误、缓存和来源隔离；不以相同地址或共享总线通道推断相同对象。
- DHCSR、SysTick CTRL 等读副作用项只允许明确的手动单次读，禁止自动轮询、批量探测或复位值扫描。状态检测继续复用 GDB/OpenOCD 的状态来源，不直接轮询 DHCSR。
- 按寄存器、实际通道和后端能力决定 NeedHalt，允许已证明可用的安全 MMIO 运行态读取；未知路线仍拒绝。不得因支持运行态 MMIO 而放开 GDB 寄存器堆或借核指令。

### C. Cortex-R52

- 完整描述并接通常用身份、控制和 MPU：MIDR、MPIDR、SCTLR、HSCTLR、CPACR、HCR、MPUIR、HMPUIR、PRSELR、HPRSELR、MAIR0/1、HMAIR0/1，以及实际容量范围内的 EL1/EL2 MPU region。每项核对编码、宽度、主要字段、访问条件与手册来源。
- 统一普通 CP15、MPU 和 selector 的权限判断。区分停止前 CPSR/DSPSR 与当前 Debug state；不能用保存的模式、halt 状态或用户配置代替当前 Debug EL、执行状态及必要授权/trap 证据。
- 可靠证据必须绑定实际核心、后端、会话和当前读取事务。无法证明权限时，在数据指令前返回明确 Unknown/Restricted；已证明合法的路径必须实际成功读取，不能把全部请求返回 Unknown 当作完成。
- 指令注入保留在 OpenOCD，复用已有生产后端、协议、服务锁、保存恢复、回读和异常隔离。TUI 只负责描述、门禁、请求、证据和显示，不重写另一套注入状态机。
- selector 在单个受保护事务内完成保存、选择、读取和恢复；异常、取消、超时、恢复不确定时不得发布部分成功值或继续盲目注入。必要 scratch 和 selector 恢复必须有验证。
- 仅在执行前明确“命令不支持”且另一条路径已获验证时允许选用该路径；实际注入故障后不自动换后端重试。保持目标或服务的故障隔离状态可见。
- 保留 R52+ 目录入口，但身份与差异未验证时明确 Unknown/Unsupported，不能因目录与 R52 相同而宣称硬件适配完成。
- 无法证明的低 EL、Guest 或 trap 场景可保持受限；本版不通过改模式、权限或控制寄存器获取访问。完整低 EL/Guest 支持另列里程碑。

### D. ADS 参考、界面与生命周期

- 参考 Arm Development Studio 的 Core/SIMD/System 分组、Name/Value/Size/Access 列、字段/枚举树、说明、S/D/Q 别名、进制/浮点格式及 Unavailable 原因展示。优先复验已有实现，不以寄存器条目数量相同为验收标准。
- 使用 `docs/registers-development-todo.md` 中的 ADS 截图和已有本地核对记录理解表现；交付定义依据公开文档独立维护，不依赖 ADS 安装，不分发其专有 XML。
- 分别显示未实现、后端不支持、NeedHalt、NeedEnable、权限受限、Unknown、读取失败和过期值。失败不得显示为 0；保留旧值时同时保留原始采样时间、owner、路线和来源，并标为过期。
- 核切换、帧切换、运行/暂停、复位、重连、目录/路由变更及共享 owner 变化时正确失效。迟到或上下文变化后的响应不得覆盖当前值；运行态 MMIO 的有效性依其实际采样边界判断。
- 仅为启用且当前需要读取的项目产生 I/O，不无条件扫描全部目录；纯展开、搜索、格式、说明和状态查看不产生额外读取。无启用项时不轮询，不增加固定 tick 空转。
- 验收按需读取时记录空闲 CPU、内存及目标请求计数的前后结果；使用相同配置和测量方法，确认新增面板没有引入空闲轮询或持续资源增长。无需为此建立新的长期性能测试平台。
- 多核共享调试资源的访问沿用既有协调和事务机制；GDB 在线时运行控制仍由 GDB 执行，不通过 Tcl 抢发 halt/resume/step，不依赖全局 target 切换维持路线。

## 六、测试与证据

不执行上板测试，不等待硬件可用。完成与本版相匹配的单元测试、MI/Tcl 集成及实际 EXE/CLI 入口测试；软件夹具只证明其覆盖的协议、状态机或算法，不宣称等同 ARM 实板。

重点验证：

1. 旧配置、每核覆盖、目录路径、继承、来源及非法输入在连接前拒绝。

## 七、迭代方式、输出与提交

按紧密相关的 feature 形成可审查批次：公共模型/配置 → M 目录及门禁 → M 动态探测/CorePrivate/运行态 → R52 权限及事务 → 界面生命周期/文档 → 完整验收/发布。依据现有实现调整顺序，避免重复完成已经验收的工作，不把该顺序变成新的范围。

每轮自检前序任务的验收是否仍适用，并检查本轮改动影响的依赖和边界；没有受到影响的前序项目沿用已有证据。发现回归时修复并复验受影响项目，保留失败原因与最终证据。完整回归放在阶段边界和发布前，不在每个小改动后重新执行。

每轮必须输出并记录：

1. **完成了什么**：feature ID、实际行为及必要改动。
2. **还有什么未完成**：本版剩余 ID 与具体缺口；后续范围和硬件待执行另列。
3. **[已完成 feature 数]/[未完成 feature 数]**：固定总数 36，不能混用旧 TODO 数量。
4. **测试结果及限制**：测试入口、通过/失败/跳过、证据位置，未执行硬件明确 SKIPPED。
5. **提交与推送**：开发分支名、提交 SHA、远端核验结果。

每个有完整改动的迭代提交并推送 `codex/register-debugging`，仅提交本轮相关文件。纯状态检查不制造空提交。失败时报告真实原因，不声称已提交或已推送。

遇到重复失败先分析根因，改变处理方法，不重复同一构建/测试/下载来消耗时间。缺少硬件按本目标跳过；范围外问题记后续；必要信息或外部服务确实阻塞时说明具体缺口，继续可以独立完成的本版工作，不用静默等待或无意义循环替代进展。每轮应推进 feature、修复具体缺陷或补齐缺失证据；只有重复测试或状态叙述不算一次开发迭代。持续输出有实质内容的阶段更新。
